## Summary

- **Segments.** The kernel answers "for whom does this work?" for subgroups the caller declares in advance, with an interval per segment, a wider family-wise interval that accounts for how many were looked at, and one heterogeneity test before any two are compared. It does not search for subgroups. The decision layer now reads them: an action that materially harms a declared segment cannot be automated whatever the pooled effect says, and segments the analysis could not estimate are not treated as cleared. Declaring no subgroups adds no checks — that is not evidence the effect is uniform, only that nobody asked.
- **Causal numbers the platform serves.** They come from `packages/causal-core`. The backend's `effect_estimate` and `identification_check` skills delegate to it, and so does the API; agents reach it through `packages/causal-mcp`, the one MCP server. Without observational data they return no estimate and say why; the old graph-heuristic numbers and the constant interval are gone. Ground truth is gated by the pre-registered T0, LaLonde (T3), IHDP (T2), segments (T4), difference-in-differences (T5), anytime-valid monitoring (T6), cluster-randomized (T7), switchback (T8) and Rosenbaum sensitivity (T9) benchmarks.
- **Staggered rollouts.** `design="difference_in_differences"` with `unit` and `time` columns estimates group-time effects, with unit-clustered intervals and an event study. It is tier C: the result rests on parallel trends, which data cannot prove, and a failed pre-trends test makes it `contested`. The comparison is never-treated units, or with `control_group="not_yet_treated"` the units not yet treated, for a rollout that reaches everyone. With `covariates` (time-invariant only) parallel trends need hold only among units alike on them, and each effect is doubly robust (Sant'Anna & Zhao): consistent if either the propensity or the outcome model is right (T5 v4). Where the outcome model is wrong the intervals sit near the floor of the coverage band: 0.932 in the registered run, 0.914–0.942 on development seeds. Unbalanced panels, treatments that switch off, covariates that vary within a unit and poor overlap are refused with a typed reason; anticipation, repeated cross-sections and the full Rambachan–Roth machinery are not offered (`did-anticipation-cross-sections` and `did-rambachan-roth` on the register).
- **Randomized rollouts that are watched, clustered or switched.** All three are `design="randomized"` with one more column. With `sequence`, a canary read at every look gets an anytime-valid confidence sequence instead of a fixed-sample interval re-read (T6). With `cluster`, clusters (services, tenants) are randomized and units inside them measured, with CR2 cluster-robust intervals on t(K − 2), and the analysis refuses when cluster sizes vary so much that a few clusters dominate (T7). With `cluster` as the time block plus `time` and `washout`, it is a switchback: one system switched between arms by block, a declared washout dropped from the start of every block, block means compared (T8). The washout has to cover the carryover. A carryover check makes the result `contested` when the effect is still moving after the washout (T8 v2: power 0.918 against a carryover that biases the estimate by three standard errors, false alarms 0.054–0.061), but it misses one whose bias is a fraction of a standard error (0.095), so the washout should still come from knowledge of the system.
- **Whether an agent may act on those numbers.** `packages/causal-decision` turns an outcome into one of four verdicts (`act`, `act_with_approval`, `experiment`, `refuse`) from a policy the caller sets, and returns the experiment that would settle an unsettled question. It is deterministic and gated by the pre-registered D0 suite. It decides; it does not execute, and nothing yet checks whether the decisions were *right* — that is the calibration row below.
- **What was decided is kept.** `POST /api/v1/decisions` analyses and rules in one call — nothing can change the evidence in between — and seals the result into an append-only hash chain with the digests it rested on. `/api/v1/decisions/verify` recomputes the chain from the stored rows and names the first entry that fails. That detects tampering inside this platform's trust boundary. `/api/v1/decisions/checkpoint` returns a head to publish elsewhere and `/api/v1/decisions/verify-anchored` checks the chain against such checkpoints; nothing publishes one yet, so anchoring is `partial` on the register.
- **The assumptions a verdict rested on are kept, and a revision says what it breaks.** A causal model is registered once (`/api/v1/models`) and revised into immutable, content-addressed versions: the kernel's graph, each edge with its origin and review status, plus the assumptions a graph cannot state. A revision may propose edges but not approve them; approving is a review, role-gated, and nobody reviews an edge they introduced. A decision can name a version instead of sending a graph, the ledger records which, and `GET /api/v1/models/{name}/impact` answers, for every decision made on an older version, whether its estimate still stands if the new graph is true — gated by the pre-registered A0 suite against an oracle that shares no code with the kernel.
- **What is still heuristic, and labelled so.** `counterfactual_reason` and `intervention_estimate` return triage scores with `heuristic: true` and a caveat. No counterfactual is computed. Discovery is not implemented.
- **The kernel's own limits** are on the register too: triangulation at moderate n, overlap detection and general-ID estimation.
- **LLMs.** No LLM is called anywhere. The agents are rule-based code.
- **Governance.** A Guardian verdict now authorises exactly one write: it is signed by the issuer, names the object it was issued for and the action it rules on, and is spent on use, so it cannot be forged by inserting a row, replayed against a second write, or pointed at a different object -- and approving an object takes a verdict issued for `GOVERNANCE_APPROVE`, not one from a check for some other action. The `/check` → `/approve` flow completes through the API when the caller classifies the situation; an unclassified one is still refused by PR-006. `/reject` needs the same kind of verdict, APPROVED and issued for `GOVERNANCE_REJECT` on that object, so a classified rejection completes too; it used to need a REJECTED verdict, which only an unclassified check produced (septa-53). The numbers the rules judge are the platform's: PR-002 scores the submitted narrative against the kernel outcome it reports, and a request that supplies its own score or cycle count is refused. Approving or rejecting records what the person said, as text, in a row that is deliberately unsigned so a record of a decision can never be spent as authority for the next one. Every state-changing route is now checked against one role matrix (`backend/src/middleware/rbac.py`), and a token's `domains` claim bounds which semantic objects its holder lists, reads, drafts into and reviews; on PostgreSQL the database enforces that scope again with row-level security, fed per request and binding `causal_app`, the role the backend connects as. Deciding an intervention needs a governance role, and the `audit_write` skill records a request as PENDING instead of letting an agent write down that it passed.
- **Gates.** `.gnomon/ci.sh` is the gate, and GitHub Actions runs that same script: green on `main` (run 36159843491, 19 steps passed, 1 named skip: frontend eslint, which had no config until this branch). The workflow fails on exit 1 or 2, so a skipped step (a broken environment) cannot read as a pass, and turns 3 into a warning. The script exits 0 (passed), 1 (a step failed), 2 (a step could not be measured) or 3 (an advisory regressed: documents are owed a re-read); only 0 is done. It includes security steps: bandit (MEDIUM and above held at zero), a secret scan of the working tree, and pip-audit and npm audit, which fail on any advisory not excused by a dated entry in `scripts/audit-allowlist.json` and are not measured, so CI fails, when the advisory database is unreachable. `scripts/verify.sh` execs it, and `.septacore.json` declares it as the repository's one blocking step, so `septacore check` runs the same gate.
